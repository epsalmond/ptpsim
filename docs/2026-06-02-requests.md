## Context

The client application iOS app consumes the ptpsim manifest/FFI as the camera-knowledge
engine. Post-rebuild the app has one `Camera` with transports; each transport
opens a PTP/IP `CameraAPISession`. Two exist today:

- **`app`** — BLE → Wi-Fi-AP (reference app mobile profile).
- **`wireless-tether`** — network-direct PTP/IP (camera in wireless tether mode
  on the LAN; live-view = `0x9018` SdkGetLiveViewData poll).

A 2026-06-02 real-GFX100 II device test of the rebuilt UI on the **wireless-tether**
transport: live-view is solid, but **shutter and image-transfer fail**. Root cause
is a manifest gap, not (only) app code: the bundled `gfx100ii.yaml` models the
`app` transport fully (shooting + reference app mode-20 image-transfer) but `wireless-tether`
has only live-view (`0x9018`) + a few absolute property controls. Capture and
transfer are not modeled for it.

## Manifest audit (2026-06-02) — precise schema/data gaps

Audited `gfx100ii.yaml` `connections.*.entries` + `operations`. The app already walks
`modeEntry(connection, from, to)` plans (it IS manifest-driven for mode entry), so these
are manifest gaps, not app bugs — each needs an upstream schema or data change.

### Gap 1 (SCHEMA + DATA) — image-transfer-from-live-view is modeled in-session; the camera needs a fresh PTP/IP session

`app` entry `to: image-transfer, from: shooting/stills` models `sendOp 0x1018` →
`setProp 0xdf01=0x14` + `0xdf28/0xd226/0xd227` → vendor prime `0x9054/0x9055/0x9050/0x9053`,
all on the SAME socket. The wire (MODE_CHANGES §5 + IMAGE_TRANSFER_FW0230, on-device
verified) shows reference app **re-establishes the PTP/IP session** between Take and Get:
`0x1018 → CloseSession(0x1003) → 8-byte 0xffffffff transport-close sentinel → new
InitCommandRequest (same GUID+name+tail) → OpenSession → 0xdf01=0x14 + setup`. Wi-Fi stays
up; only the TCP socket reopens. An in-session switch makes the camera reject `0x9054`
(verified on device) — this is the "image transfer downloads 0 files" bug.
- **Schema:** the verbs (`setProp/getProp/readEcho/sendOp`) can't express a socket reopen.
  Add a step verb, e.g. `reopenSession` (close sockets, send the sentinel on the command
  socket, reconnect, re-run InitCommandRequest+OpenSession with the same identity).
- **Data:** insert `reopenSession` between `0x1018` and `0xdf01=0x14` in that entry (and the
  cold `to: image-transfer` entry if reachable from an open session).

### Gap 2 (SCHEMA + DATA) — the capture / take-cycle is not modeled

`0x100e` is gated in `operations` but its sequence is hardcoded in the app: `0x100e` →
event-socket awaits `0xc004 CapturePending` → `0xc001 PostviewComplete` → `readVendor9022`
postview → `0x400d CaptureComplete`. No manifest plan expresses this.
- **Schema:** an operation-sequence / capture model expressing the trigger op, event-socket
  awaits (by event code), and an **optional** postview read (the `readVendor9022` over-stream
  download — likely not a launch feature, so it must be expressible as optional).
- **Data (app):** the take cycle above. **Data (wireless-tether):** capture is just `0x100e`
  on the command socket — no event socket, no postview (shoots to card). My current Swift
  `0x100e` branch should become this manifest plan.

### Gap 3 (DATA) — shooting/video mode is not modeled

`modes` has `shooting`, `shooting/stills` but no `shooting/video`. The flip is one in-session
property write — `0xD246` (app, UINT8 0/1) / `0xD037` (wireless-tether, 1=stills/257=video)
per the app-mode-flips captures. Add `shooting/video` + a per-connection entry (prop differs
by connection).

### Gap 4 (DATA) — wireless-tether has no entries at all

`wireless-tether` lists `modes: [shooting/stills, remote-trigger]` but has no `entries:` — no
live-view entry, no capture, no transfer; the app hardcodes all of it (`0x9018` poll live-view
+ the `0x100e` capture branch). Add `wireless-tether` entries: `to: shooting/stills` (`0x9018`
poll; no `0x101c`), capture (`0x100e`), and an `image-transfer` mode using the standard PTP
object model (`0x1007`→`0x1008`/`0x100a`→`0x1009 GetObject`), NOT the app mode-20 flow.
(Pending a wireless-tether transfer capture for the exact enumeration + handle filtering vs the
live-view virtual handle `0x80000001`.)

**Flag (FUJI_PTP_PROP_REFERENCE, 2026-06-02):** that ref lists `0x9018 SDK_GetLiveViewData` as
"not used over Wi-Fi", yet the manifest models `0x9018` as wireless-tether's live-view op and the
app bridges it. wireless-tether live-view was never device-validated (the 2026-06-02 device test
was the `app`/55740 path). Please reconcile the actual wireless-tether (15740/PCSS) live-view +
capture mechanism before modeling G4 — the `0x9018` assumption may be wrong.
